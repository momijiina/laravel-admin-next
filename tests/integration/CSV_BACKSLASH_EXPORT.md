# Literal backslashes in CSV exports

The built-in `CsvExporter` now uses standard CSV quote doubling with an empty
escape argument. Backslashes remain literal data in header and row values.
Previously, PHP's proprietary backslash escape prevented a quote immediately
after a backslash from being doubled. A standard reader could then lose quotes,
split fields, or treat an embedded newline as the next record. For example,
text containing `before\"quote` could not be exported and read back exactly.

The change applies to populated and empty headers, ordinary cells, and results
from exporter title/column callbacks. The comma separator, double-quote enclosure,
UTF-8 BOM, response headers, column selection/order, export scopes, and callback
timing retain their behavior. Exports without backslashes retain their existing
bytes. A backslash by itself no longer forces a field to be enclosed; a quote
after any number of backslashes is now doubled like every other embedded quote.

## Reader and customization compatibility

PHP readers should explicitly disable the proprietary escape as well:

```php
$row = fgetcsv($stream, null, ',', '"', '');
```

For `SplFileObject::fgetcsv()`, set the same controls with
`$file->setCsvControl(',', '"', '')` before reading.

Account for the existing UTF-8 BOM before parsing the first header, as required
by the consuming reader. Omitting the escape argument is deprecated in PHP 8.4;
passing `'\\'` explicitly still changes how backslash/quote sequences are read
and can misread standard CSV, including fields that end in a backslash. Changing
only the writer does not change a consumer's reader settings.

Review consumers that compare exact CSV bytes containing backslashes or assume
PHP's old escape convention. Previously downloaded files retain their original
bytes; regenerate affected exports when necessary. Custom exporters or overrides
of `CsvExporter::export()` must adopt equivalent header and row writing to receive
the fix. No dependency, schema, published view, or asset changes are needed.

## Regression coverage

`CsvBackslashExportTest.php` uses the existing real HTTP-kernel/SQLite export
fixture and the actual stream-and-exit exporter in a child process. It parses
the result with an explicitly empty CSV escape and compares exact field arrays.
Coverage includes one and multiple backslashes before quotes, terminal
backslashes, commas, Unicode, embedded newlines, final-column values, title and
column callbacks, and empty table/filter/selected/current-page results.
An `originalValue()` case preserves raw JSON with quotes, backslashes, Unicode,
zero and null while bypassing the displayed label and exporter column callback.
Named and unnamed grids exercise filtered/sorted all/current-page/selected
exports; 106 matching records cross the 100-record chunk boundary.
Production diagnostics and nonempty subprocess stderr fail the tests.

The unchanged exporter fails **6 of 11 tests** on PHP 8.4.27 with both Laravel
12.70.1 and 13.38.0. The fixed exporter passes **11 tests / 159 assertions** on
both. The existing CSV headers, default driver, driver registry and object-display
group also passes **26 tests / 1,967 assertions** per framework after its readers
adopt the explicit empty escape. The standalone CSV regression checks
hand-written expected bytes, including backslash/quote fields, independently of
`fputcsv()`.
An independent local check feeds the real HTTP export to Python's
`csv.reader(strict=True)` on both frameworks and preserves all 107 records and
four columns with mixed Unicode, commas, quotes, newlines and trailing backslashes.

Run with the [integration consumer setup](README.md):

```sh
composer test -- --filter CsvBackslashExportTest
```

These checks cover generated bytes and PHP parsing. They do not establish live
browser download behavior, spreadsheet import behavior, non-SQLite database
coverage, or compatibility with arbitrary consumer exporters/readers.
